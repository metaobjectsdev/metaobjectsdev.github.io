One typed model for every app that shares your data

Your agent writes the model. Each app's code is generated from it, and each app's build is checked against it.

OpenAPI and TypeSpec keep an API contract honest. They don't reach the database schema behind it, or the prompts your LLM features fill from the same data, and rules files and Markdown specs only tell an agent what should be true: nothing fails when the code stops matching them. So one field change still touches the migration, the API types in each language and the prompt inputs, and a coding agent working in one of them can't see the others.

MetaObjects puts them in one typed model: the data, the API contract, the prompt payloads, and the features the software is supposed to have. Each app generates its types, validators and routes from it, in its own language, and the output depends on no proprietary runtime; the same model drives migrations and the live-database check. Each app's verify step fails CI when its generated code, a prompt template or a declared feature no longer matches, and the Node meta verify --db does the same for the database in any language. If partners call your API, keep OpenAPI and oasdiff at that edge: MetaObjects does not export OpenAPI yet, and it does not compare a change with your last release.

Less code to write and review. You, or your coding agent, write one declaration in the model instead of the same thing once per layer: the types, validators, queries, routes and UI. The generators write the rest. In one app, 18 model objects become 129 generated files. In another, 13 become 117.

Write it once. Generate it for every entity. Any layer you repeat for every entity (API client, DTO mapping, audit log, admin screen, docs) becomes a small generator in your repo, so it can't drift from the model and nobody hand-writes it again. The shipped generators (Drizzle, Spring, EF Core, FastAPI and more) run as they are or can be copied in and changed.

It protects what the model declares; your hand-written logic is still yours. If your app is single-language with no LLM calls, a good ORM is probably enough, and the comparison below says so up front.

What fails the build

A field renamed in one service misses the worker that reads the same table. A required field reaches the API but not the Python model that mirrors it. A prompt template still says {{userName}} after the payload moved to user.name. Each of these looks fine inside the one codebase an agent is editing. Here is what MetaObjects 1.2 checks, the command that runs the check, what happens when it fails, and where it does not reach.

When this happens What fails, and how Where it runs today
The shared model changes and one app or service is not regenerated That app's verify exits 1 and lists the generated files that no longer match the model. It checks generated files; your hand-written code that calls them is caught by your compiler once you regenerate (Python: with mypy or pyright). All five ports. TS meta verify --codegen · Python metaobjects verify · Java and Kotlin mvn metaobjects:verify · C# dotnet meta verify --codegen. Each app runs its own check in its own CI; nothing links the apps for you.
A prompt or output template (email, export, docs) uses a field its typed payload doesn't carry — or the payload field was renamed ERR_VAR_NOT_ON_PAYLOAD, exit 1, with the template file and line. A missing template file fails too. A payload field the template never uses is not flagged. Templates are Mustache in every port, or Jinja in Python and TypeScript: the check walks the parsed Jinja template, and a reference it cannot settle without running the template fails with ERR_TEMPLATE_NOT_STATIC instead of passing. All five ports for Mustache; Jinja in Python and TypeScript (Java, Kotlin and C# refuse a Jinja body by name). A bare verify runs it in every port once a template root is configured.
The live database no longer matches the model — a column renamed, missing or extra meta verify --db <url> exits 1 and lists the column differences. On Postgres it applies the model's schema to a throwaway database and compares the two catalogs, so columns, types, defaults, CHECKs, indexes and view bodies are compared in Postgres's own spelling. The Node meta CLI, for any port's database: Postgres, SQLite, Cloudflare D1. Not MySQL, SQL Server or Oracle.
The model lives in another repo and its publisher changed it meta verify --deps exits 1 with ERR_DEPENDENCY_UPSTREAM_DRIFT. Opt-in; it needs the publisher's checkout path. TypeScript publishes. Python, Java, Kotlin and C# load the committed, hash-locked snapshot and refuse a stale one (Java, Kotlin and C# since 1.2). Syncing the snapshot and the upstream check run in the Node meta CLI.
Someone hand-edits a generated file, then the model changes The edit is never silently overwritten. TypeScript three-way merges it on the machine that generated the file (a conflict leaves markers and fails); elsewhere, and in a fresh CI checkout, regeneration refuses the file by name. In TypeScript, meta verify --codegen lists hand-edited files as a notice; add --forbid-hand-edits to fail the build on any hand edit. All five ports refuse to overwrite. Three-way merge: TypeScript only.
A requirement marked live points at a field or route that was renamed or removed ERR_REQUIREMENT_DANGLING_REF, exit 1. A live requirement that names nothing implementing it is a warning, or a failure with --require-implementers. It proves the links resolve, not that the code is correct. All five ports, on every verify run.

Since 1.2 a bare verify runs the same three checks in every port: generated code, templates and the requirement links. The database and cross-repo checks stay opt-in, so name --db and --deps in CI if you use them.

Write your own generators

The checks above only protect code that is generated. Every layer you still write by hand for each entity is one more unchecked copy of the model, so write a generator for each layer that repeats per entity. Change the model, regenerate, and verify --codegen fails the build for anyone who forgot. Running a shipped generator as it is works too.

A generator is small: a name plus a function from the loaded model to a list of { path, content } files. The runner writes them, and verify --codegen re-runs it and fails the build when the committed output is stale. This one, from the write-your-own-generator recipe, writes one file per entity listing its fields, inherited ones included: 

import { isAbstract, perEntity, type Generator } from "@metaobjectsdev/codegen-ts";

export function fieldListGenerator(): Generator {
  return {
    name: "field-list",                          // shows in diagnostics
    filter: (obj) => !isAbstract(obj),           // ctx.entities has EVERY object, abstract ones too
    generate: perEntity((obj) => ({              // perPackage / perModel for other scopes
      path: `field-list/${obj.name}.txt`,        // relative to outDir
      content: obj.fields()                      // fields() includes inherited fields
        .map((f) => `${f.name}: ${f.subType}${f.resolvedIsArray() ? "[]" : ""}${f.isRequired ? "" : "?"}`)
        .join("\n") + "\n",
    })),
  };
}

What it costs, measured

Three agent sessions each wrote a first generator from scratch, using only the public docs and packages: a typed fetch client for TypeScript (172 lines), an audit log for TypeScript (148 lines, plus 32 that declare its model markers), and a typed httpx client for Python (203 lines). Each session took 8 to 10 minutes of agent time end to end, setup included. Each generator passed verify --codegen on its first run and failed it after a model change that was not regenerated. Each had to read shipped generator source for details the docs don't state yet. Java, Kotlin and C# use the same shape and were not measured.

These are our own measurements, so check them: model Customer and Order, run the shipped entity and route generators, then write your own generator that emits a typed API client for those routes, and wire it so verify --codegen covers it.

The fastest test of fit is one generator of your own

Pick a layer you hand-write for every entity and write that one generator. Then rename a field in the model. If the generator plus its output is smaller than the copies it replaces, and the rename fails the build, that is your answer. If not, stop there.

What owning one means

A generator you write has no upstream copy, so there is nothing to fall behind. A shipped generator you eject does: fixes to it no longer reach your copy, so run shipped ones as shipped until you need them to differ. Only TypeScript has a scaffold command. meta gen does not typecheck a generator, so run tsc on it in CI. A one-off layer that won't repeat can stay hand-written.

Who it's for, and who it isn't for yet

Several apps on one data model

A TypeScript API and a Python LLM worker reading the same Postgres. A Spring service and a React admin app. Put the apps in one repo and point each at the same model directory, and each app's build fails when it falls behind. Any mix of the five languages works.

Prompts and output templates filled from your data

A prompt or output template (email, export, docs) is a template, Mustache or (in Python and TypeScript) Jinja, plus a payload. When the payload is a type generated from the model, a renamed field fails the build instead of quietly sending the LLM an empty slot. Render, payload types and the drift check ship in all five ports, and so do typed response parsers for prompts that declare a response. Jinja templates stay Jinja in Python and TypeScript; Java, Kotlin and C# render Mustache only.

Code that agents write

The checks above run in CI whether or not the agent remembered what the other services assume, and the model is small YAML or JSON an agent can read and edit.

Partly: separate repos on the JVM or .NET

Since 1.2 a Java, Kotlin or C# service in its own repo can build from a shared model: it loads a committed, hash-locked snapshot and refuses a stale one. Fetching that snapshot and checking whether the publisher moved still run in the Node meta CLI, and publishing a model as a Maven or NuGet package is not built yet.

Not for: SQL Server or Oracle schema management

Migrations and the live-database check cover Postgres, SQLite and D1. On SQL Server or Oracle, MetaObjects won't manage the schema; the contract types and the prompt and requirement checks still work beside your ORM.

Probably not: one app, one language, no LLM

If a single service owns its data and talks to no LLM, Prisma, Hibernate, EF Core or Django already give you one schema. The layers you repeat per entity are still generated for you, and the cross-app and prompt checks are what you would add MetaObjects for.

One model keeps your apps consistent at build time. It does not check wire compatibility during a rolling deploy or for outside API consumers, and verify does not stop a team that ignores the model and keeps its own DTO.

If the tool falls short, you can fix it. Most changes a team needs are to generated output: your own generators are already yours, and eject copies any shipped one into your repo to change the same day. For the core (loader, verify, migrate, render) it is Apache 2.0 with all five ports in one public repo: patch a fork, pin to it, and drop the patch when upstream catches up. Every upstream release you then want is a merge you do.

If you already work spec-driven

Spec Kit, Kiro and OpenSpec get a feature started well: a spec, a plan and a task list in Markdown, then the agent writes the code. After the first iteration nobody updates the Markdown, each service re-derives the same types slightly differently, and nothing fails when the code and the spec drift apart. A Markdown spec is read by the agent. It is not checked by the build.

They work together: a feature spec names model entities instead of copying their fields, and the agent changes the model first, then regenerates. What the check proves is that the code matches the model, not that the feature behaves correctly, so you still need tests for behaviour.

Using it with the ORM you have

You don't have to leave Prisma, Hibernate, EF Core or SQLAlchemy. Every port can generate just the types and validators (the API contract and the prompt payloads) and leave persistence to the ORM you already run. One exception: in TypeScript, MetaObjects can write your schema.prisma from the model, and verify fails when someone edits it by hand or it falls behind. Otherwise it does not generate into your ORM's schema files; they stay yours, and MetaObjects sits beside them.

Databases. Generated code is tested against Postgres in every port, and against SQLite and MySQL for parts of it. meta migrate and the live-database check support Postgres, SQLite and Cloudflare D1; on MySQL you own the DDL. SQL Server and Oracle are not supported today: the C# AppDbContext generator emits Postgres column types, and the Java runtime's older Oracle and SQL Server drivers are untested. If you run on either, generate the contract types above and keep your own mapping.

Check your own repo first

The fit and migration assessment is one Markdown prompt that your coding agent runs against your repo. It needs no database connection or signup. The agent reads your code, migrations and commit log and writes a report. The main part is a list of the drift in your own history: shapes you declare in more than one place, where those copies disagree today, and past fixes that patched one copy and missed the other. For each one, it names the verify check that would have failed the build instead.

With your repo open in your agent, send one message (read-only, no install, no signup)

Fetch https://metaobjects.dev/assess.md and run the MetaObjects
Fit & Migration Assessment against this repository.

Works in Claude Code, Cursor, Windsurf, GitHub Copilot, Gemini CLI, or any agent that can fetch a URL; pasting the prompt into any chat works too. It runs on your tokens, and results vary by model. Every claim cites a file:line or a commit so you can check it. Nothing is sent to us. The quick pass answers in the conversation and writes nothing; the full assessment takes an hour or more and writes its report outside your repo.

Read it first. /assess.md is the whole prompt, in plain Markdown. It is read-only: it tells your agent to read your repo and report, and never to create, edit, install or commit anything in it. The same prompt, with its reference files, is in the repo at a release tag.

The assessment can tell you not to adopt. Each pillar gets its own verdict, and NOT A FIT is one of the options. It only promises what your language's port ships, and every report includes a "what you will NOT get" section. We ran it blind on a production codebase from before that codebase adopted MetaObjects. It found drift incidents, confirmed in git, that had already caused trouble: a constraint mismatch that was fixed only after it was violated in production, and a schema divergence that was still live when the assessment ran. Where it was wrong, it understated the problems rather than overstating them.

What it includes

  • Codegen. Native code in all five languages on each one's usual stack (side by side below), compiled and run in CI. Nothing generates until you opt in (since 1.0.4), and eject copies a shipped generator into your repo in every port since 1.0.5. Write your own generators.
  • Runtime metadata. Load the model at runtime to drive CRUD, validation, relationships and dynamic admin UIs, in TypeScript, Java, Kotlin and Python (C#: roadmap; its EF Core output is generated code, not a metadata-driven runtime). Typed tool payloads are declared today, and MCP tool exposure is on the roadmap.
  • Drift detection. Every port's verify covers generated code and prompts, and live-database schema drift runs in the Node meta CLI for Postgres, SQLite and D1. What fails the build lists each check and its command.
  • Prompt construction. A typed payload, prompt text in a file resolved per provider, and deterministic rendering that you can snapshot-test and that keeps exact-prefix prompt-cache hits. Prompts that declare a response get a typed parser. All of it ships in all five ports; MCP exposure is on the roadmap. Read: Prompts are code now, and OpenAI says so.
  • Requirements and testing. A capability is a node in the model, and verify checks that what it names exists. Since 1.1.0 the gate runs in every port's verify and every port ships a requirement-tests generator; the authoring lint is TypeScript-only. Checking that declared features exist, and how capability requirements work.
  • Libraries. Design you won't differentiate on, such as "libraries": ["iam"], declared once and opted into by name. Since 1.0.4 the library models load in all five ports, and meta eject copies one into your repo to own. ai (LLM-call tracing, generated in TypeScript, Java and Python) is stable; iam (users, groups, roles, grants) is a preview.
  • Sharing a model across your own projects. One project publishes part of its model and another consumes a hash-locked snapshot; meta verify --deps says when the publisher's model moves. The TypeScript toolchain publishes, over a folder path or an npm or Python package; TypeScript, Python, Java, Kotlin and C# projects consume. Maven and NuGet packaging is a later phase.

Checking that declared features exist

Drift checks cannot see a second failure: your code agrees with your model, and the model describes a capability your software does not have. The columns exist, the types match and the tests pass, but no code ever writes the value.

This is for teams that have to prove what their software implements: regulated, audited, or built to a contract. Declared across three shipping products, that check found a bot that could not be retired, a season that could not be run privately, private tables silently running at the database default, and an interrupted-work recovery path that was never built, in a codebase with 1,280 tests passing and zero failures. A capability declared in MetaObjects is a node in the same model as your entities, and verify checks that the field or route it names exists.

Where MetaObjects earns its setup is several apps or services sharing one model, especially in more than one language or with prompts filled from that data, because that is the drift no single-codebase tool, and no single smarter agent, can see. If you already use OpenAPI or TypeSpec

      
A schema-first API already gives you much of this: TypeSpec or OpenAPI as the source, a generated TypeScript client and Pydantic models, a step in CI that regenerates and runs git diff --exit-code, and oasdiff or buf breaking against the last release. If your problem is a public or partner API, keep that. Those tools are standard and mature, and they check compatibility across versions, which MetaObjects does not.

        If the API contract is the only thing that drifts, use the IDL. If the database, the API types in two or more languages and the prompts drift from each other, that is three pipelines that don't know about each other, and MetaObjects replaces them with one model and one check. A team with partners on its API may want both, and today that means keeping the OpenAPI spec in step with a generator you write.
      

    


    
    

      

        
For AI agents

        

          Every contract is grep-friendly (named constants, never magic strings), and generated code is plain code in each language. Your agent (Claude Code, Cursor, GitHub Copilot, Windsurf) edits the model files and the generators write the code.

    • 
          
  • CLAUDE.md in the repo: agent instructions for working in the metaobjects codebase itself
    • 
        

        

          Why Claude Code in particular. MetaObjects was designed around Claude Code from the start. The model vocabulary fits in a context window, conformance is checked by the build rather than found at runtime, and an agent can read the generated code without knowing a framework's internals. A first-party MCP server exposing the spec, conformance fixtures, and codegen tools as agent-callable functions is on the roadmap.

Who builds it, and how you can help

      

        MetaObjects is an open-source project led by its creator, Doug Mealing, who wrote its first version in 2001 and rebuilt it in the open in 2026, with coding agents doing much of the typing. Today it has one human maintainer. The README says so, and the GitHub contributor list and the npm, PyPI, NuGet and Maven owners show it. That is the biggest risk in adopting it, and the fix is more maintainers.
      

      
    
        
  • Own a port. Each port has its own code and docs, and a shared conformance suite fails when a port disagrees with the others. A port can have its own maintainer who never needs to read the other four.
    • 
        
  • Own a generator family. The shipped generators for each stack (FastAPI, Spring, EF Core, React) are small and ejectable. Owning one means its issues, its review and its release notes are yours.
    • 
        
  • Fix what readers hit. The gaps on this page are filed issues: SQL Server, Oracle, Maven and NuGet packaging of shared models and a JSON Schema and OpenAPI emitter.
    • 
      

      

        What a co-maintainer gets. Credit by name in MAINTAINERS.md and in the release notes. Review and merge rights on the part you own after a run of merged pull requests, and publish rights for a port you own. A vote on the model format and on design decisions. A co-maintainer who owns a port gets first call on paid work in that port. The rules are in GOVERNANCE.md and MAINTAINERS.md.
      

      

        How to start. Read CONTRIBUTING.md, then pick an open issue or open one that says which port or generator you would like to own. Run scripts/ci-local.sh --quick before a pull request: CI on a pull request runs the tests and the conformance corpus for each port it touches (the Docker integration suites run on release tags). Reviews take days, not hours.
      

      

        Need help adopting it? The creator takes a few paid consulting engagements at a time, through metaobjects.com: an architecture review of whether it fits, a pilot of one slice built with your team, help writing your first generators, and support while you pilot. It is one person, so capacity is small and the open-source project comes first. Paid work funds the maintenance.
      

    


    

      
Where it came from

      

        Built by one person since 2001. Open now, and looking for co-maintainers. The idea is old; the code, and the project around it, are new. It was used privately for 25 years on secure messaging, payments, online gaming and pharmaceutical regulatory systems, and one approach from it is patented in the US. It was set aside in 2022 and is now open source for the first time, rebuilt for AI coding agents.
