Apache 2.0 · TypeScript · Java · Kotlin · C# · Python

One typed model for every app that shares your data. Your agent writes it, each app's code is generated from it, and each app's build is checked against it.

Coding agents get context — rules files, memories, MCP servers — and context is advisory: nothing fails when the code stops matching it. That gets worse when several apps share one data model. Your API, your LLM worker, your admin app and your prompts can each look right on their own and still disagree with each other, and a smarter agent working on one of them can't see the others. MetaObjects gives them one typed model — data, API contract, prompt payloads, and what the software is supposed to do. Each app generates its types, validators and routes from it, in its own language, with no proprietary runtime in the output. Each app's verify step fails CI when its generated code, a prompt, or a claimed capability no longer matches the model.

Generate. The boring parts are derived from the model, in five languages — at build time as code you own, or at runtime from the live model.
Verify. The build fails when generated code drifts from the model and when a prompt's payload no longer matches what it's told — and it fails or warns when a feature someone marked done has nothing implementing it.

It protects what the model declares; your hand-written logic is still yours. You can keep your ORM. And if your app is single-language with no LLM calls, a good ORM is probably enough — the honest comparison says so first.

Context is advisory. This is not: here is exactly what fails the build.

A field renamed in one service misses the worker that reads the same table. A required field reaches the API but not the Python model that mirrors it. A prompt template still says {{userName}} after the payload moved to user.name. Each of these looks fine inside the one codebase an agent is editing. Here is what MetaObjects 1.1 checks, the command that runs the check, what happens when it fails, and where it does not reach.

When this happens What fails, and how Where it runs today
The shared model changes and one app or service is not regenerated That app's verify exits 1 and lists the generated files that no longer match the model. It checks generated files; your hand-written code that calls them is caught by your compiler once you regenerate. All five ports. TS meta verify --codegen · Python metaobjects verify · Java and Kotlin mvn metaobjects:verify · C# dotnet meta verify --codegen. Each app runs its own check in its own CI; nothing links the apps for you.
A prompt or output template (email, export, docs) uses a field its typed payload doesn't carry — or the payload field was renamed ERR_VAR_NOT_ON_PAYLOAD, exit 1, with the template file and line. A missing template file fails too. A payload field the template never uses is not flagged. Templates are Mustache, logic-less: no expressions or filters, so a computed value belongs in the payload. All five ports. TS and C# run it by default; Python --templates; Java and Kotlin -Dmeta.verify.mode=templates.
The live database no longer matches the model — a column renamed, missing or extra meta verify --db <url> exits 1 and lists the column differences. The Node meta CLI, for any port's database: Postgres, SQLite, Cloudflare D1. Not MySQL, SQL Server or Oracle.
The model lives in another repo and its publisher changed it meta verify --deps exits 1 with ERR_DEPENDENCY_UPSTREAM_DRIFT. Opt-in; it needs the publisher's checkout path. TypeScript publishes and checks; Python can consume the snapshot but not run the check. Java, Kotlin, C#: not yet.
Someone hand-edits a generated file, then the model changes The edit is never silently overwritten. TypeScript three-way merges it on the machine that generated the file (a conflict leaves markers and fails); elsewhere, and in a fresh CI checkout, regeneration refuses the file by name. In TypeScript, meta verify --codegen lists hand-edited files as a notice; add --forbid-hand-edits to fail the build on any hand edit. All five ports refuse to overwrite. Three-way merge: TypeScript only.
A requirement marked live points at a field or route that was renamed or removed ERR_REQUIREMENT_DANGLING_REF, exit 1. A live requirement that names nothing implementing it is a warning, or a failure with --require-implementers. It proves the links resolve, not that the code is correct. All five ports, on every verify run.

One thing to set up deliberately: in TypeScript a bare meta verify runs the prompt and requirement checks only. Name --codegen (and --db or --deps if you use them) in CI. The ports differ in their defaults, so the commands above are the ones to copy.

Who needs this — and who doesn't, yet.

Several apps on one data model

A TypeScript API and a Python LLM worker reading the same Postgres. A Spring service and a React admin app. Today each keeps its own copy of the schema and they drift. Put the apps in one repo, point each at the same model directory, and each app's build fails when it falls behind. Any mix of the five languages works.

Prompts and output templates filled from your data

A prompt or output template (email, export, docs) is a Mustache template, logic-less, plus a payload. When the payload is a type generated from the model, a renamed field fails the build instead of quietly sending the LLM an empty slot. Render, payload types and the drift check ship in all five ports, and so do typed response parsers for prompts that declare a response. If your prompts are Jinja or carry logic, expect to move that logic into the payload.

Code that agents write

An agent working in one service doesn't know what the other services assume. The checks above run in CI whether or not the agent remembered, and the model is small YAML or JSON an agent can read and edit.

Not yet: separate repos on the JVM or .NET

Sharing one model across repos with an upstream check works when the consumer is TypeScript (Python can consume, not check). A Kotlin, Java or C# service in its own repo can only vendor a copy of the model today, with nothing telling it the original moved. Keep those services in one repo with the model, or wait for Phase 2.

Not for: SQL Server or Oracle schema management

Migrations and the live-database check cover Postgres, SQLite and D1. On SQL Server or Oracle you can still use the contract types, prompt checks and requirement checks beside the ORM you have, but MetaObjects won't manage that schema.

Probably not: one app, one language, no LLM

If a single service owns its data and talks to no LLM, Prisma, Hibernate, EF Core or Django already give you one schema. The cross-app and prompt checks are the reason to add MetaObjects; without them the setup may not pay for itself.

One model keeps your apps consistent at build time. It does not check wire compatibility during a rolling deploy or for outside API consumers, and verify does not stop a team that ignores the model and keeps its own DTO.

MetaObjects has no independent adopters yet. Every project on this page is maintainer-owned, so the cheapest way to find out whether it fits yours is the read-only assessment on your own repo.

Keep your ORM. Generate the contract around it.

You don't have to leave Prisma, Hibernate, EF Core or SQLAlchemy. Every port can generate just the types and validators — the API contract and the prompt payloads — and leave persistence to the ORM you already run. MetaObjects does not generate into your ORM's schema files; it sits beside them.

Databases, plainly. Generated code is tested against Postgres in every port, and against SQLite and MySQL for parts of it. meta migrate and the live-database check support Postgres, SQLite and Cloudflare D1; on MySQL you own the DDL. If you run on either, generate the contract types above and keep your own mapping.

Watch the introduction

The problem MetaObjects solves, what it actually is, and how the codegen and runtime halves work together — in eight minutes.

Don't take the table's word for it. Ask your own git history.

MetaObjects ships a hosted fit & migration assessment: one Markdown prompt your coding agent runs against your existing repo. Read-only, propose-only — it installs nothing, edits nothing, needs no database connection and no signup. Your agent reads the code, the migrations, and the commit log, then writes a decision-grade report whose centerpiece is a drift ledger built from your own history: the shapes you declare twice, where the copies disagree today, the past fixes that patched one copy and missed the other — and, per finding, the verify gate that would have made it a build failure instead of an incident.

With your repo open in your agent, send one message — read-only · no install · no signup

Fetch https://metaobjects.dev/assess.md and run the MetaObjects
Fit & Migration Assessment against this repository.

Works in Claude Code, Cursor, Windsurf, GitHub Copilot, Gemini CLI — any agent that can fetch a URL. No agent open right now? Read the assessment prompt — it's one Markdown file; pasting it into any chat works too. The catch, stated plainly: it runs in your agent on your tokens, findings vary by model, and every claim is cited to a file:line or a commit precisely so you can check it. Nothing is sent to us; the report stays in your repo.

It's built to say no. Per-pillar verdicts include NOT A FIT, every promise is capped to what your language's port actually ships, and a "what you will NOT get" section is mandatory. In a blinded retro-test on a real pre-adoption production codebase, the assessment found specific, git-verified drift incidents that had already bitten — a constraint mismatch repaired only after a production violation, a schema divergence still live at assessment time — and its errors ran conservative, not inflated.

What is underneath the two verbs.

Codegen

One metadata model → native code in five languages, on each language's usual stack: Drizzle + Zod + Fastify/Hono (TS), Spring REST + DTO + repositories (Java), Exposed + KotlinPoet + Spring (Kotlin), EF Core + ASP.NET (C#), Pydantic + FastAPI (Python). Hand edits to generated files are never silently overwritten; in TypeScript they are three-way merged on regeneration. The generators are reference helpers, not the product: copy any of them into your repo with eject and the copy is yours to change. What MetaObjects guarantees is the model, the loader, migrate, verify and prompt render.

All five ports; every generator's output is compiled, and the generated APIs are run, in CI. Eject in every port since 1.0.5: meta eject, metaobjects eject, mvn metaobjects:eject, dotnet meta eject. Opt-in since 1.0.4: nothing generates until you choose.

Runtime metadata

Load metadata at runtime and drive behavior dynamically — CRUD, validation, relationships, dynamic admin UIs. (Typed tool payloads are declared today; MCP tool exposure is on the roadmap.)

TypeScript, Java, Kotlin, Python. C#: roadmap — its EF Core output is generated code, not a metadata-driven runtime.

Drift detection

Each port's verify compares the committed generated code with a fresh generation from the model and fails when they differ, so an app that wasn't regenerated after a model change fails its own build. Once you regenerate, your compiler catches the hand-written code that still uses an old name. The table at the top lists every check and its command.

All five ports for generated code and prompts. Live-database schema drift runs in the Node meta CLI, for every port's database (Postgres, SQLite, D1).

Prompt construction

The prompt is code too — not a string scattered across services. Declare a typed payload as a projection, keep the text external and provider-resolved, render deterministically: snapshot-testable, cache-stable (no stray whitespace silently breaking exact-prefix prompt-cache hits), drift-checked at build time so a renamed field can't quietly degrade a prompt. Plus typed parsers for the LLM's response, on prompts that declare one — Zod / Pydantic / Jackson / kotlinx.serialization / System.Text.Json across the ports.

Render, payload types, verify and parsers in all five ports. MCP exposure of declared prompts: roadmap.

Requirements and testing

A capability is a node in the same model as your entities, so implementedBy is resolved, not trusted — a claim whose implementation vanished fails the build, and one naming nothing is a warning. verify reports the ledger on every run. It proves the links resolve, not that the implementation is correct.

Since 1.1.0 the requirement gate runs in every port's verify, and every port ships a requirement-tests generator; the authoring lint is TypeScript-only (docs). Dogfooded on maintainer-owned projects, no outside adopter yet.

Read: capability requirements →

Libraries

Design you didn't invent and won't differentiate on, declared once and opted into by name: "libraries": ["iam"]. Entities, the requirements they promise, and the generators they imply arrive as one drift-gated artifact. The core layer adds no tables; the schema is a separate iam/db opt-in. meta eject copies one into your repo to own.

Since 1.0.4 the library models load in all five ports; the ai trace helper generates in TypeScript, Java and Python. ai (LLM-call tracing): stable. iam (users, groups, roles, grants): preview.

Sharing a model across your own projects. One project publishes part of its model — a common Customer, an audited base, a set of enums — and another declares it as a dependency, syncs a committed, hash-locked snapshot, and builds on it with extends and references. When the publisher's model moves, meta verify --deps says so instead of two copies drifting apart. Today the TypeScript toolchain publishes and TypeScript and Python projects consume, over a path dependency (a sibling checkout or submodule). Java, Kotlin and C# arrive in Phase 2. The meta deps commands and verify --deps run in the Node meta CLI.

The failure after drift: the feature your agent said it built.

Drift is your code disagreeing with your model, and meta verify already makes that a build error. There is a second failure it cannot see: your code agrees with your model perfectly, and the model describes a capability your software does not have. The columns exist, the types line up, the tests pass — and no code path ever writes the value. Nothing is broken, so nothing fails.

This is for teams that have to prove what their software implements: regulated, audited, or built to a contract. It is a smaller audience than the checks above, which is why it sits below them.

Declared across three shipping products, that check found a bot that could not be retired, a season that could not be run privately, private tables silently running at the database default, and an interrupted-work recovery path that was never built — in a codebase with 1,280 tests passing and zero failures. A capability declared in MetaObjects is a node in the same model as your entities, so its link to the field that implements it is resolved rather than trusted.

Fields aren't just columns. They carry validators, views, and currency formatting as child metadata.         The honest read: for a 5k-line TS app with no LLM integration, Drizzle is probably enough. Where MetaObjects earns its setup is several apps or services sharing one model — especially in more than one language, or with prompts filled from that data — because that is the drift no single-codebase tool, and no single smarter agent, can see. For a multi-language team in one repo (TS + Python, TS + Java, or all five), no other system in this matrix generates and checks every app from one model.
      

    


    
    

      

        
Built so AI agents work at the metadata layer.

        

          Every contract is grep-friendly (named constants, never magic strings). Generated code is plain per-language code, not framework magic. An llms.txt index ships at the root so any agent fluent in the convention can index the full standard in seconds. The substrate is designed so Claude Code, Cursor, GitHub Copilot, and Windsurf edit metadata files — and the codegen handles every language behind them.

          Why Claude Code in particular. Anthropic's official CLI was the day-zero driver for the standard's design choices. The metamodel vocabulary is small enough to fit in a context window; the conformance contract is enforced by a build gate rather than discovered as runtime drift; and the generated code is plain code an agent can read without a framework's internals in its head. A first-party MCP server exposing the spec, conformance fixtures, and codegen tools as agent-callable functions is on the roadmap.
